---
title: ESLint plugin
description: Run native GraphQL lint rules and JavaScript custom rules with a GraphQL-ESLint-compatible parser.
---

`@graphql-analyzer/eslint-plugin` combines native graphql-analyzer rules with
JavaScript custom rules in ESLint. Its default parser supplies the
GraphQL-ESLint custom-rule API. Built-in rules run in Rust; custom JavaScript
rules run in ESLint.

The parser compatibility does not remove every built-in rule or configuration
difference. Review the [migration guide](/graphql-analyzer/linting/migrating-from-graphql-eslint/)
before replacing an existing GraphQL-ESLint setup.

## Install

The plugin supports ESLint 8.40+, 9.x, and 10.x with flat config, and requires
`graphql` version `^16.5.0`. Use a Node.js version supported by your ESLint
version; the native addon supports Node.js 18+. Install the plugin and its
GraphQL peer dependency:

```sh
npm install --save-dev @graphql-analyzer/eslint-plugin graphql@^16.5.0
```

npm installs the native addon for macOS ARM64/x64, Linux ARM64/x64 with glibc,
or Windows x64 through platform-specific optional dependencies.

## Configure native rules

Configure schema and documents in the GraphQL project configuration. You can
also set native rule defaults there:

```yaml
# .graphqlrc.yaml
schema: schema.graphql
documents: "src/**/*.{graphql,js,ts}"
extensions:
  graphql-analyzer:
    lint:
      rules:
        noAnonymousOperations: error
        noDuplicateFields: error
        alphabetize:
          - warn
          - selections: [OperationDefinition]
```

Select the rules and their ESLint severities in flat config:

```js
// eslint.config.mjs
import graphql from "@graphql-analyzer/eslint-plugin";

export default [
  {
    files: ["**/*.graphql"],
    languageOptions: { parser: graphql.parser },
    plugins: { "@graphql-analyzer": graphql },
    rules: {
      "@graphql-analyzer/no-anonymous-operations": "error",
      "@graphql-analyzer/no-duplicate-fields": "error",
      "@graphql-analyzer/alphabetize": ["warn", { selections: ["OperationDefinition"] }],
    },
  },
];
```

The native engine discovers the nearest supported GraphQL config file and
selects the matching project in multi-project configurations. ESLint rule
entries enable native rules and forward their options to Rust. Explicit
ESLint options take precedence over the corresponding GraphQL config options.

The presets expose ESLint rule maps. Use a preset's `.rules` field in place
of the rule map above. Available presets are:

- `flat/schema-recommended`
- `flat/operations-recommended`
- `flat/schema-all`
- `flat/schema-relay`
- `flat/operations-all`

## Write custom rules

Custom rules receive GraphQL nodes through ordinary ESLint visitors and
selectors. The following rule requires an operation name to start with `App`:

```ts
// app-operation-name.ts
import type { GraphQLESLintRule } from "@graphql-analyzer/eslint-plugin";

export const appOperationName: GraphQLESLintRule = {
  meta: { type: "suggestion", schema: [] },
  create(context) {
    return {
      OperationDefinition(node) {
        if (node.name && !node.name.value.startsWith("App")) {
          context.report({ node: node.name, message: "Start operation names with App." });
        }
      },
    };
  },
};
```

After compiling the rule, register it with ESLint and use `graphql.parser`:

```js
import graphql from "@graphql-analyzer/eslint-plugin";
import { appOperationName } from "./app-operation-name.js";

export default [
  {
    files: ["**/*.graphql"],
    languageOptions: { parser: graphql.parser },
    plugins: { internal: { rules: { "app-operation-name": appOperationName } } },
    rules: { "internal/app-operation-name": "error" },
  },
];
```

The custom-rule interface includes:

- GraphQL node visitors, selectors, and `:exit` listeners.
- `node.rawNode()` for the graphql-js AST node and `node.typeInfo()` for its
  type-information snapshot.
- `context.sourceCode.parserServices.schema` and `.siblingOperations`.
- `requireGraphQLSchema` and `requireGraphQLOperations` helpers, plus public
  `GraphQLESLintRule` and node/service types.
- ESLint reports, suggestions, fixes, and ordinary `RuleTester` usage.

Schema and document services load during parsing. Type-information snapshots
are computed on demand. The services support GraphQL config
discovery and project selection, inline `parserOptions.graphQLConfig`, and
`parserOptions.schemaSdl`. For example, a schema-aware custom rule can use:

```js
languageOptions: {
  parser: graphql.parser,
  parserOptions: {
    schemaSdl: "type Query { hello: String }",
  },
}
```

These parser options configure JavaScript custom-rule services. They do not
configure the native engine, which uses its own GraphQL config discovery.

## Lint embedded GraphQL

Apply the compatible processor to host files and the GraphQL parser to its
virtual documents:

```js
import graphql from "@graphql-analyzer/eslint-plugin";
import { appOperationName } from "./app-operation-name.js";

export default [
  {
    files: ["**/*.js"],
    processor: graphql.processor,
    rules: { "no-debugger": "error" },
  },
  {
    files: ["**/*.graphql"],
    languageOptions: { parser: graphql.parser },
    plugins: {
      "@graphql-analyzer": graphql,
      internal: { rules: { "app-operation-name": appOperationName } },
    },
    rules: {
      "@graphql-analyzer/no-anonymous-operations": "error",
      "internal/app-operation-name": "error",
    },
  },
];
```

The processor preserves the host source for its parser and rules. It extracts
GraphQL into named virtual `.graphql` files and maps reports, suggestions, and
safe fixes to the original file. The named form, `processor: "@graphql-analyzer/graphql"`,
is also available when the plugin is registered under `@graphql-analyzer`.
Configure your usual TypeScript or framework parser when applying the processor
to those languages:

| Host extension        | Host parser                        |
| --------------------- | ---------------------------------- |
| `.js`, `.mjs`, `.cjs` | ESLint's default JavaScript parser |
| `.ts`, `.tsx`         | `@typescript-eslint/parser`        |
| `.vue`                | `vue-eslint-parser`                |
| `.svelte`             | `svelte-eslint-parser`             |
| `.astro`              | `astro-eslint-parser`              |

Keep each host parser in a config block matching that extension. When needed,
configure its TypeScript parser through `languageOptions.parserOptions.parser`.
Host parsers are not bundled with this plugin.

Compatibility tests cover recognized imports and aliases, global tags,
GraphQL magic comments, multiple blocks, interpolation gaps, CRLF, Unicode,
and Vue/Svelte/Astro script blocks. The compatibility processor uses
GraphQL Tools plucking and respects `extensions.pluckConfig`. Framework
plucking requires the corresponding loader dependencies in your project:
`@vue/compiler-sfc`, `svelte` with `svelte2tsx`, or `astrojs-compiler-sync`.

Fixes that cross interpolation gaps or could change host literal syntax are
suppressed. Do not assume every JavaScript string containing GraphQL can be
extracted or safely fixed.

Native embedded checks use the native extractor on the physical file. Its
supported forms are narrower: recognized imported tags are supported, while
interpolated templates and GraphQL magic comments are not. Compatibility
processor support for a form does not imply native-rule support for that form.

## Choose native-only mode

For native rules without JavaScript GraphQL custom rules, select
`graphql.fastParser` on `.graphql` files:

```js
languageOptions: {
  parser: graphql.fastParser;
}
```

For native embedded checks, select `graphql.fastProcessor` on host files and
keep the host-language parser. Enable native rules directly on those host
files because this processor does not create virtual GraphQL documents.

The fast entry points avoid loading the compatibility parser, config loaders,
and plucking frontend. They do not provide GraphQL visitors, tokens, or parser
services to custom rules.

The compatible parser adds JavaScript AST construction and ESLint traversal.
Both modes use the native engine for built-in rules, but their performance
depends on the workload. ESLint timings are not interchangeable with CLI or
LSP timings.

## Native project lifecycle and limits

Repeated linting uses the supplied source, including unsaved edits. The native
engine checks known dependency metadata for disk changes and refreshes changed
schema or sibling files. Unchanged disk contents do not replace unsaved
overlays. Switching configs reloads the native project.

Native refresh checks known files; it does not rescan schema or document globs
for new files on every lint. Reload the native project to discover newly added
schema files; directly linting a new operation document also registers that
document. Custom JavaScript services rescan their local globs. Native metadata
checks still add work proportional to the number of
known files for each physical file linted. On non-Unix systems, an external
same-length edit that preserves the modification timestamp can evade the
native dependency fingerprint.

Native rules expose autofixes for `alphabetize` and suggestions where the
analyzer provides them. Spec-validation names are exported as no-op rules;
registering them does not emit the native validation diagnostic stream through
ESLint. See the [migration guide](/graphql-analyzer/linting/migrating-from-graphql-eslint/)
and [rules catalog](/graphql-analyzer/rules/catalog/) when choosing rules.
