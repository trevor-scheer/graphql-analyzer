---
title: Migrating from @graphql-eslint/eslint-plugin
description: Move GraphQL custom rules and supported native rules to graphql-analyzer while preserving required ESLint checks.
---

`@graphql-analyzer/eslint-plugin` supports GraphQL-ESLint custom rules through
its default parser and processor. Shared native rules retain their
GraphQL-ESLint names, but configuration, validation-rule exports, and autofix
coverage still differ. Check those differences before removing the upstream
plugin.

## Update the parser and rule registration

Install the plugin and its GraphQL peer dependency:

```sh
npm install --save-dev @graphql-analyzer/eslint-plugin@alpha graphql@^16.5.0
```

Change the parser import and any native rule prefixes you want to migrate:

```diff
- import graphql from "@graphql-eslint/eslint-plugin";
+ import graphql from "@graphql-analyzer/eslint-plugin";

  export default [
    {
      files: ["**/*.graphql"],
      languageOptions: { parser: graphql.parser },
-     plugins: { "@graphql-eslint": graphql },
+     plugins: { "@graphql-analyzer": graphql },
      rules: {
-       "@graphql-eslint/no-anonymous-operations": "error",
+       "@graphql-analyzer/no-anonymous-operations": "error",
      },
    },
  ];
```

ESLint plugin keys are configurable. You can keep an existing key when
registering the analyzer plugin, but its preset rule maps use
`@graphql-analyzer`. The available preset names are
`flat/schema-recommended` and `flat/operations-recommended`.

## Configure native rule options

Enable native rules and their options under
`extensions.graphql-analyzer.lint` in your GraphQL config:

```yaml
# .graphqlrc.yaml
schema: schema.graphql
documents: "src/**/*.graphql"
extensions:
  graphql-analyzer:
    lint:
      rules:
        noAnonymousOperations: error
        alphabetize:
          - warn
          - selections: [OperationDefinition]
```

Keep the corresponding ESLint rule entries to select which diagnostics ESLint
reports. Native rule options in ESLint's `rules` object are not forwarded to
Rust. The native engine supports one project per config; inline
`parserOptions.graphQLConfig` configures custom-rule services only.

## Keep custom rules

Keep `graphql.parser` for JavaScript GraphQL rules. It provides node visitors,
selectors, exit listeners, `rawNode()`, `typeInfo()`, and schema and sibling
services. Import the public `GraphQLESLintRule` types and the
`requireGraphQLSchema` and `requireGraphQLOperations` helpers from
`@graphql-analyzer/eslint-plugin` when updating your own rules.

Custom-rule schema services support config project selection,
`parserOptions.graphQLConfig`, and `parserOptions.schemaSdl`. These do not
extend the native engine's config support. Use ESLint's ordinary `RuleTester`
with the compatible parser for custom-rule tests.

For embedded custom rules, use `graphql.processor` on host files and match
virtual documents with `files: ["**/*.graphql"]`. Keep the host-language
parser and rules on the original files. See the
[embedded configuration example](/graphql-analyzer/linting/eslint-plugin/#lint-embedded-graphql).

## Preserve validation rules you need

GraphQL-ESLint exports spec-validation rules such as `known-type-names`,
`fields-on-correct-type`, and `no-undefined-variables`. The analyzer plugin
does not export those ESLint rules. Native analysis performs validation
internally, but its rule shims do not expose that complete diagnostic stream
as configurable ESLint rules.

Do not delete a required validation rule solely because native analysis runs
similar checks. You can retain upstream validation rules alongside native
rules using the compatible parser:

```js
import analyzer from "@graphql-analyzer/eslint-plugin";
import upstream from "@graphql-eslint/eslint-plugin";

export default [
  {
    files: ["**/*.graphql"],
    languageOptions: { parser: analyzer.parser },
    plugins: {
      "@graphql-analyzer": analyzer,
      "@graphql-eslint": upstream,
    },
    rules: {
      "@graphql-analyzer/no-anonymous-operations": "error",
      "@graphql-eslint/known-type-names": "error",
    },
  },
];
```

This configuration keeps the upstream package installed for the rules you
still use. Configure its custom-rule schema services through the compatible
parser as needed.

## Choose a mode and check remaining differences

Use the default `parser` and `processor` when running custom GraphQL rules.
Use `fastParser` and `fastProcessor` only for native rules. The fast entry
points avoid JavaScript GraphQL AST construction and compatibility-loader
imports, and provide no GraphQL visitors or parser services to custom rules.

Other differences to check include:

- Flat config is required; `.eslintrc` is unsupported.
- Native autofix exposure is limited to `alphabetize`. Custom-rule fixes and
  suggestions work through ESLint, with unsafe embedded edits suppressed.
- Compatible embedded extraction supports more forms than native extraction.
  Native interpolated templates and GraphQL magic comments are unsupported.
- Native dependency refresh covers known files. New schema files matching
  globs require project reload. New operation documents require project reload
  or direct linting before native rules see them. Custom services rescan local
  globs.
- CLI, LSP, and ESLint have different execution costs. Compatibility adds
  JavaScript parsing, AST allocation, and ESLint traversal.

The plugin also provides `operation-name-suffix`, `redundant-fields`,
`require-id-field`, and `unique-names`, which are not shared upstream rules.
See the [rules catalog](/graphql-analyzer/rules/catalog/) before enabling them.

## Earlier alpha rule names

If your config uses an earlier graphql-analyzer rule name, update it to the
shared GraphQL-ESLint name:

| Earlier alpha name | Shared rule name |
| --- | --- |
| `@graphql-analyzer/unused-fields` | `@graphql-analyzer/no-unused-fields` |
| `@graphql-analyzer/unused-fragments` | `@graphql-analyzer/no-unused-fragments` |
| `@graphql-analyzer/unused-variables` | `@graphql-analyzer/no-unused-variables` |

The corresponding GraphQL config keys are `noUnusedFields`,
`noUnusedFragments`, and `noUnusedVariables`.

## Verify your migration

The plugin's parity fixtures compare shared-rule counts, messages, message
identifiers, source positions, and fixes against GraphQL-ESLint. Custom-rule
tests separately exercise the parser contract and embedded source mapping.
Those fixtures do not cover every combination of options and project setup.

Run your existing lint checks and custom-rule tests with the new configuration.
Compare the results before removing upstream rules or dependencies. If a
supported rule behaves differently, [report the failing example](https://github.com/trevor-scheer/graphql-analyzer/issues).
